## Summary
PR #697 (fix for #2214) moved the conversation store to IndexedDB and cut quotes to one level, but the pending-send outbox (zustand persist name "openim-pending-outbox-v1", default localStorage storage, apps/chat-to/src/lib/im/pending-outbox.ts) still writes synchronously into the shared ~5MB origin quota with no try/catch. When localStorage is near full, an offline send (or an online send that fails with a retryable error) throws QuotaExceededError out of sendOpenIMMessage: the message is never written to the outbox, the bubble flips to the red failed icon immediately instead of the clock, and the console logs "failed to send message QuotaExceededError ... openim-pending-outbox-v1" - the exact line Henry hit on prod at 02:11 on 10/9 right after the #2214 hotfix was deployed. Reproduced on chat-test build test-20261009-114941-40 (commit eec519d48, includes PR #697).

## Steps to reproduce
1. Log in to chat-test.teamily.ai (yuxiao+03) and open a group chat (AG3-share).
2. Bring localStorage close to the quota, e.g. in DevTools: localStorage.setItem("qa-quota-filler", "f".repeat(5062440)) - on a ~5.24M-char quota this leaves ~600 chars of headroom. (Realistic equivalent: the old "conversation" localStorage key that PR #697 leaves in place, plus member-cache / contact / Group / profile caches.)
3. Go offline (DevTools > Network > Offline, or any network drop).
4. Send a text message.
5. Control: remove the filler key and repeat steps 3-4.

## Expected result
The offline send is held in the pending outbox (clock icon, 1 item persisted) and resent on reconnect. A failed persist must never abort or fail the send - the same principle PR #697 applied to the conversation store ("a failed write cannot throw into the caller").

## Actual result
Console: failed to send message QuotaExceededError: Failed to execute "setItem" on "Storage": Setting the value of "openim-pending-outbox-v1" exceeded the quota (thrown from the zustand persist middleware). localStorage["openim-pending-outbox-v1"] stays {"state":{"items":{}}} (0 items). The bubble shows the red failed icon immediately; header says "Waiting for network". Control run with free storage: outbox has 1 pending item (907 chars), bubble shows the clock, delivered on reconnect. Note: in the failing run the Rust SDK in-memory reconnect resend still delivered the text once because the tab stayed open (server seq 12); what breaks is the persistence guarantee - reload / tab close while offline, media (ByFile) resends that re-register OPFS bytes from the outbox item, and online sends that fail with a retryable error (Henry path on 10/9), which rely on the JS outbox alone.

## Severity
- **Level**: High
- **Frequency**: Always

## Environment
- **Platform / OS / Browser**: Web (chat-test.teamily.ai, headless Chromium 1600x900 via Playwright); desktop app shares the same code path

## Additional context
- **Feature area**: IM / message sending / pending outbox persistence
- Code: apps/chat-to/src/lib/im/pending-outbox.ts persist({ name: "openim-pending-outbox-v1", partialize: items }) with the default localStorage storage and no try/catch; upsertItem() is called from enqueuePendingMessage() in both the offline path and the retryable-failure path of sendOpenIMMessage().
- Still on localStorage after #697 (same unguarded persist pattern): openim-pending-outbox-v1, member-cache, contact, Group, im-user-profile-cache, server, auth. The old "conversation" localStorage key is left in place by #697 ("no longer read or written"), so users who hit #2214 before the fix keep up to several MB of dead data in the shared quota.
- Suggested fix: wrap the persist storage so a QuotaExceededError never propagates into the send path (persist failure = lose reload-survival only, not the send), or move the outbox to IndexedDB via createIdbPersistStorage like the conversation slice; plus a one-time localStorage.removeItem("conversation") cleanup.
- Evidence: screenshots 06 (failing run: red icon while offline) and 08 (control: clock) attached; console excerpt attached; server-side pull_msg_by_seq on sg_957854985 shows each test message exactly once (seq 10-13). Related: #2214, TensorOpera-Inc/chat-web PR #697, Henry 10/9 02:11 report in Payment & Team Subscription Dev.

## 摘要
PR #697（#2214 的修复）把会话列表迁到了 IndexedDB、引用只嵌一层，但待发送队列（zustand persist 名 "openim-pending-outbox-v1"，默认 localStorage，apps/chat-to/src/lib/im/pending-outbox.ts）仍然同步写入同一个约 5MB 的域配额且没有 try/catch。localStorage 快满时，断网发送（或在线发送失败走重试队列）会从 sendOpenIMMessage 抛出 QuotaExceededError：消息根本没写进队列，气泡立刻变成红色失败图标而不是时钟，控制台报 "failed to send message QuotaExceededError ... openim-pending-outbox-v1"，与 Henry 10/9 02:11 在生产部署 #2214 热修后撞到的报错完全一致。已在 chat-test 构建 test-20261009-114941-40（commit eec519d48，含 PR #697）复现。

## 复现步骤
1. 登录 chat-test.teamily.ai（yuxiao+03），打开一个群聊（AG3-share）。
2. 把 localStorage 填到接近配额，例如 DevTools 执行 localStorage.setItem("qa-quota-filler", "f".repeat(5062440))，在约 5.24M 字符的配额下只剩约 600 字符余量。（现实等价物：PR #697 留在原地不清理的旧 "conversation" key，加上 member-cache / contact / Group / 用户资料缓存。）
3. 断网（DevTools > Network > Offline，或任意掉网）。
4. 发送一条文本消息。
5. 对照：删掉填充 key，重复第 3-4 步。

## 预期结果
断网发送被待发送队列接住（时钟图标，队列里持久化 1 条），重连后补发。持久化失败绝不能打断或判失败发送，这和 PR #697 对会话列表采用的原则一致（"写失败不能抛给调用方"）。

## 实际结果
控制台：failed to send message QuotaExceededError: Failed to execute "setItem" on "Storage": Setting the value of "openim-pending-outbox-v1" exceeded the quota（从 zustand persist 中间件抛出）。localStorage["openim-pending-outbox-v1"] 保持 {"state":{"items":{}}}（0 条）。气泡立刻显示红色失败图标，顶部显示 "Waiting for network"。对照组存储充足时：队列有 1 条 pending（907 字符），气泡是时钟，重连后送达。说明：失败那轮因为标签页一直开着，Rust SDK 的内存重连队列仍把这条文本补发了一次（服务端 seq 12）；真正坏掉的是持久化保证——断网时刷新/关标签页、媒体消息（ByFile）靠队列项从 OPFS 重新登记字节、以及在线发送失败走重试队列（Henry 10/9 的路径），这些只依赖 JS 队列。

## 补充信息
- **功能区域**: IM / 消息发送 / 待发送队列持久化
- 代码：apps/chat-to/src/lib/im/pending-outbox.ts 的 persist({ name: "openim-pending-outbox-v1", partialize: items }) 用默认 localStorage 且无 try/catch；sendOpenIMMessage() 的断网路径和可重试失败路径都经 enqueuePendingMessage() 调到 upsertItem()。
- #697 之后仍在 localStorage 的同款无兜底 persist：openim-pending-outbox-v1、member-cache、contact、Group、im-user-profile-cache、server、auth。旧的 "conversation" key 被 #697 留在原地（"不再读写"），所以修复前撞过 #2214 的用户，共享配额里还占着最多几 MB 的死数据。
- 建议修法：给 persist 的 storage 包一层，QuotaExceededError 绝不传播进发送路径（持久化失败只损失刷新后续发能力，不影响发送）；或像会话列表一样用 createIdbPersistStorage 迁到 IndexedDB；并做一次性 localStorage.removeItem("conversation") 清理。
- 证据：截图 06（失败轮：断网时红色失败图标）和 08（对照：时钟）已附；console 节选已附；服务端 pull_msg_by_seq 拉 sg_957854985 显示四条测试消息各落库一次（seq 10-13）。关联：#2214、TensorOpera-Inc/chat-web PR #697、Henry 10/9 02:11 在 Payment & Team Subscription Dev 群的报告。
