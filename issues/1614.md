## Summary
On 2026-09-10 16:01:36 (UTC+8) an onboarding sync message was sent into group 2213724931 (Session Replay & Onboarding) whose mention segment read @12236097754431223609775443 — a 26-digit string equal to 1223609775443 concatenated twice. That string matches no member of the group, so it could not be resolved into a member and no @ notification was triggered; yet the message itself was sent successfully and returned a message ID, with no error or warning shown to the sender. This is a silent failure — the sender believes the notification was delivered when it was not.

## Steps to reproduce
1. In a group chat, send a message whose @ segment contains a malformed userID, e.g. @12236097754431223609775443 (26 digits, i.e. 1223609775443 repeated twice).
2. Send the message — it is sent successfully and returns a message ID (observed: ced731ead7421943e571e779f65689d6 in group 2213724931).
3. Check the member who should have been mentioned (real userID 1223609773775443, 16 digits) — no @ notification is received at all.
4. Control: re-send the same message with the correct userID 1223609773775443 — the send succeeds (message ID 6c89fcacfd11b4546adad721c1a9d708), confirming the group and the agent send permission are fine.

## Expected result
When the @ target userID is malformed or matches no group member, the sender should get a clear error or a degraded-mode notice (e.g. mention target invalid — sent as plain text) instead of a plain success. Ideally the send path should validate the target (digit-only + expected length) and verify membership before sending, then either reject the send or auto-correct it.

## Actual result
The message is sent successfully with no warning at all, but the @ does not take effect and the mentioned member receives no notification; the sender has no feedback and no way to detect the failure.

- **Frequency**: Always (100% no notification whenever the @ target is malformed)

- Member-table cross-check: get_groups_info(["2213724931"]) shows Tmly Quan userID = 1223609773775443 (16 digits), which does not match the malformed 26-digit string.
- Root cause: (1) the mention target was an invalid userID matching no group member, so no notification could be produced; (2) the send path performs no validation of the @ target, so the malformed id is emitted as ordinary text while the message still reports success; (3) possible aggravating factor — an agent-side send path that builds the mention by string concatenation instead of populating the structured atUserList field.
- Ruled out: group unavailable / agent lacking post permission — the same agent identity re-sent successfully into the same group with the correct userID.
- Impact: issue-sync, escalation and handoff messages that rely on @-mentions for notification can silently fail to reach the responsible owner, delaying triage and fixes, while the sender has no failure feedback and no self-check.
- Suggested fix: validate @ targets before sending (digit-only, expected length, membership); fail loudly or degrade to plain text with an explicit notice; have the agent send path populate the structured atUserList field; log/acknowledge unmatched mentions server-side so silent drops become observable.

## 摘要
2026-09-10 16:01:36（UTC+8），在群 2213724931（Session Replay & Onboarding）内发送了一条 onboarding 同步消息，其 @ 段落文本为 @12236097754431223609775443 —— 共 26 位数字，实为 1223609775443 重复拼接两次。该串不对应群内任何成员，系统无法解析成成员，因此未触发任何通知；但消息本身发送成功并返回了消息 ID，发送方没有任何报错或警告。属于静默失败：发送方误以为通知已送达，实际并未送达。

## 复现步骤
1. 在群聊中发送一条消息，其 @ 段落为一个非法 / 拼接重复的 userID，例如 @12236097754431223609775443（26 位，即 1223609775443 重复两次）。
2. 发送该消息 → 消息发送成功并返回消息 ID（实测：群 2213724931 内 ced731ead7421943e571e779f65689d6）。
3. 观察本应被提及的成员（真实 userID 1223609773775443，16 位）→ 收不到任何 @ 通知。
4. 对照组：同群同 agent 身份，@ 目标改为正确 userID 1223609773775443 重发 → 发送成功（消息 ID 6c89fcacfd11b4546adad721c1a9d708），说明群可用、agent 有发消息权限。

## 预期结果
当 @ 目标 userID 非法、或不对应群内任何成员时，发送端应给出明确的报错或降级提示（例如「提及目标无效，已按普通文本发送」），而不是直接报告发送成功。更理想的是发送前做格式校验（纯数字 + 长度符合规范）与成员存在性校验，不通过则拒绝发送或自动纠正。

## 实际结果
消息发送成功且无任何警告，但 @ 未生效，被提及人收不到通知；发送方无任何失败反馈，也无自查手段。
