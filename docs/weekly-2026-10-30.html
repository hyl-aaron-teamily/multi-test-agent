How It Runs

一份 Issue 在框架里怎么走

每一步都写进任务记录，进度精确到阶段、轮次、步骤；无论正常结束还是中途打断，都说得清停在哪一步、环境有没有恢复。

理解Issue → 意图契约→ 接口计划视图 · 六问→ 治理审批 · 版本绑定→ 运行排队 · 租环境→ 运行预检→ 感知启动 · SKILL 校验→ 执行准备：选目标并冻结→ 执行预热门→ 执行 · 感知坐标循环 ≤ 1 s→ 判定轮末判定 · 证据复核→ 治理报告 · 清单 · 轨迹→ 运行按台账恢复环境
准备期（可用 AI） 循环期（确定性，0 视觉调用） 平台：审批、任务、环境、记录

可用性：任务与环境分离

任务和环境各有自己的状态机和原子记录。操作被测软件前先记账，任务结束或中断后，由独立进程按台账恢复环境。 审批按策略分级，并绑定版本；两位状态码让 Agent 只看退出码就能决定下一步；Web 让人看清计划、环境、进度和结论。

$ autotest task run 2010/main:android-app@v1　→ 20 已排队
$ autotest task wait t-…　→ 10 未复现
faults　4 种故障 × 5 个阶段 · 20/20 恢复后照常得出结论
2.0.20　App 更新当天：重新标定 → 旧批准按版本失效 → 重新批准 → 出结论

Two Entry Points

两种入口：Agent 用命令行，人用 Web

同一套视图模型同时生成命令行文本、JSON 和 Web 页面。三种形态下，结论句、有效尝试、命中数和区间文字已在真机任务上逐项核对一致。

For Agents · CLI v1

一条命令一个动作，只看退出码

  • 覆盖 Issue、草稿、计划、环境、任务、结果六类对象的全部操作，help --json 自描述
  • --json 时 stdout 只有一个 JSON；从不提问，不会卡在交互上
  • 两位状态码，十位表示类别；附可重试标记与下一步提示
$ autotest plan explain 2010/main:android-app@v1
$ autotest task run 2010/main:android-app@v1 --max-rounds 3　20
$ autotest task wait t-20261030080949-karl　10 未复现
1x结论2x已受理3x审批4x输入 / 计划 5x环境6x工具 / 任务7x取消 / 中断0成功
For People · Web

看得懂计划，看得见环境

  • 计划审核页把每一步标在标定截图上，回答六个问题：做什么、影响什么、哪里不确定、调用几次模型、要多久、属于哪类审批
  • 环境页逐项列出基线、租约和配置项，可一键重新检查、恢复、下线
  • 结果页给出结论句、依据、证据，以及中断位置与环境恢复结果；术语悬停即可看解释

未来展望

本周把框架落了地。接下来的两个迭代在这套框架上加深感知、开放接入、扩展到探索测试，设计均已完成。

01
感知层升级（迭代四）

设备侧常驻读树服务，目标 p95 ≤ 500 ms；循环外每次点击前，先核对目标还在原处（界面树优先，像素兜底）。

02
原生 MCP 服务（迭代四）

作为标准 MCP 服务器接入 IDE 与开发环境：Issue、计划、任务、结果以工具和资源暴露，并附测试行为准则。

03
探索测试模块（迭代五）

重做自然语言任务和 AI 探索，接入任务、环境、审批和现场包；动作按风险分级，执行前先校验。

04
通用判定库

没有 Issue 时，也能识别闪退、白屏、一直加载、错误提示、占位文字、点了没反应等通用现象。

05
发现 → Issue → 复现

探索中发现的现象自动生成 Issue 草稿，交给确定性主线复现，给出带分母的结论。

06
持续回归

定时跑 SKILL 自检和已知 Issue 系列；App 一更新，就重新标定、复测。

目标：一句话或一份 Issue，就换来一份可核对、可重放、可追溯版本的结论。

人在 Web 上看得懂、管得住；Agent 在 IDE 里直接调用。确定性主线负责复现和验收，探索模块负责发现。两者共用同一套感知、执行、判定和治理能力。
