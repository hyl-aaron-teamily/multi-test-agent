## 2. 原则（继承 W2-2，本期新增）

- 继承：黑盒；循环中只按坐标操作；结论只陈述观察到的事实；环境不合格不开跑；失败分环境 / 工具；确认即冻结。
- **G1 一个核心，两种呈现**：任务、环境、计划、结果先生成视图模型（结构化 JSON，带 `schemaVersion`）；命令行文本、`--json`、Web 都由它渲染。
- **G2 状态显式且真实**：任何时刻，任务和环境的记录都能回答「在哪一步、下一步是什么」；记录与实际不符（进程已死却显示运行中）视为缺陷。
- **G3 先说明再执行**：发几条消息、发到哪、改哪些设置、调几次模型、预计多久，执行前全部列出。
- **G4 不确定点显式**：模型做的决定、依赖服务端的结果、替代执行，单独标注。
- **G5 说人话**：Web 用中文白话，术语配解释；命令行字段名稳定，每个对象带一句可读的 `summary`。
- **G6 先记账再动手**：任务每做一个有副作用的动作（进入会话、键入、发送、改设置），**先**写入副作用台账，再执行；恢复程序只依据台账和环境声明工作，不依赖任务进程还活着。
- **G7 恢复幂等**：环境恢复可以被重复执行、可以被中途打断再执行，结果一致。

## 3. P0：环境（Environment）

### 3.1 定义

环境 = 一个可以被测试任务独占使用的执行端实例。

| 字段 | 说明 |
|---|---|
| `id` | `<端>:<设备或浏览器>@<服务环境>`，如 `android-app:4f2ebdf2@prod`、`desktop-web:edge@prod` |
| 组成 | 设备（udid）/ 浏览器路径；被测包名与版本；账号；profile（坐标）与哈希；允许清单会话 |
| **环境配置项** | 环境为可测而做的系统改动，如 Taplus 黑名单。逐项声明「改什么、为什么、怎么还原」；**注册环境时由人按钮同意一次**，之后每次预检照做，不再逐计划审批 |
| **基线（baseline）** | 「干净」的可检查定义，见 §3.3 |
| 租约 | 当前占用它的任务 id、进程 pid + 进程启动时间（防 pid 复用）、租约开始时间、心跳时间 |
| 脏标记 | 上次恢复未完成 / 设备中途断开时置位；带原因 |

### 3.2 状态机

```
offline ──上线──▶ checking ──基线通过──▶ ready ──租出──▶ leased ──任务结束──▶ recovering ──基线通过──▶ ready
                      │                                   │                         │
                      ├─不合格(锁屏/离线/未登录)─▶ unfit ◀─┘(运行中断连)            └─恢复失败──▶ quarantined
                      └─恢复失败───────────────▶ quarantined（隔离：需人工，显示原因与建议动作）
任意状态 ──下线──▶ draining（不再租出；优雅结束占用任务；恢复）──▶ offline（clean | dirty）
```

- `unfit`：可自动重检（如手机解锁后）；`quarantined`：只有人点「我已处理，重新检查」才回到 `checking`。
- 任务只能租 `ready` 的环境；一个环境同时只有一个租约（文件锁 + 原子写）。

### 3.3 基线（android-app；web 同理列出）

| 项 | 检查方式（①确定性） | 恢复动作 |
|---|---|---|
| 屏幕亮、未锁屏 | `dumpsys`（预检已有） | 亮屏可自动；**锁屏不可自动**（PIN）→ `unfit`，提示「需人工解锁」 |
| 被测 App 在前台、在首页（会话列表）、无弹层 / 选择器 | 界面树 | Back / 重新启动 App |
| 台账中触碰过的会话输入框为空 | 逐个打开、读输入框 | 清空输入框（不删除、不撤回消息） |
| 键盘收起、输入法为声明的默认输入法 | `dumpsys input_method` | Back / 切回默认输入法 |
| 系统设置 = 环境配置项声明值 | `settings get` | 按声明重写 |
| 无残留进程（yadb、`uiautomator dump`、`input`） | `ps` | 结束残留进程 |
| 本机：无该任务的浏览器进程、锁文件、临时文件 | 进程表 / 文件 | 清理 |

- web 基线：任务启动的浏览器进程已结束；登录态文件（storageState）未被覆盖成无效；无残留页面。
- **不可逆的副作用不在「恢复」范围**：已在生产发出的消息不删除、不撤回（硬约束），记录在任务的副作用台账里（含运行标记），报告与结果页列出。「不影响环境」指上表各项，不指生产数据。

### 3.4 交叉检测

**上线（平台启动 / 设备接入 / 人点「重新检查」）**，对每个环境：

1. 读租约。持有者任务 T：
   - T 进程在（pid + 启动时间吻合）且心跳新鲜 → **重新接管**监控，不打断；
   - 进程在但心跳超时（> 30 s）或进度超时（> 当前步骤预算 + 60 s）→ **卡死**：杀进程树，T 记为 `failed`（状态码 62「任务卡死」），环境进入 `recovering`；
   - 进程不在 → T 记为 `interrupted`（63「任务进程意外退出」或 72「服务重启中断」），环境进入 `recovering`。
2. 扫描所有非终态任务：没有租约却显示 `running / preflight / finishing` 的，按第 1 步同样规则修正。
3. 脏标记置位 → 先恢复。
4. 基线检查 → `ready` / `unfit` / `quarantined`。
5. 每次修正写审计记录（谁、何时、修正前后状态、依据）。

**下线（平台停止 / 设备拔出 / 人点「下线」）**：

1. 环境进入 `draining`，不再租出。
2. 有占用任务 → 写取消请求，任务在步骤边界优雅停止（执行收尾）；等待 ≤ 60 s，仍未停 → 强杀进程树。
3. 设备仍可达 → 执行恢复；不可达 → 置脏标记（原因：下线时不可达），下次上线先恢复。
4. 任务记为 `interrupted`（72「环境下线 / 服务停止中断」），带停在哪一阶段、哪一轮、哪一步。
5. 平台进程收到 Ctrl+C / SIGTERM 时走上述流程；关窗口、断电等收不到信号的情况由下次上线的交叉检测兜底。

## 4. P0：测试任务（Task）

### 4.1 定义

测试任务 = 一个已批准计划在一个环境上的一次执行（系列 = 父任务 + N 个子任务）。

| 字段 | 说明 |
|---|---|
| `id` | `t-<时间>-<随机>`；系列子任务 `<父 id>.<序号>` |
| 计划 | 计划 id（`<Issue>/<子用例>:<端>@<版本>`）+ 批准时的哈希 |
| 环境 | 环境 id；租约 |
| 进度 | 阶段（预检 / 启动 / 准备 / 预热 / 循环 / 收尾 / 恢复）、轮次、步骤、最后进展时间 |
| 心跳 | 任务进程独立定时器每 5 s 写一次 |
| 副作用台账 | 追加写：进入的会话、键入的文字、发送的消息（带运行标记）、改过的设置；**先记账再执行**（G6） |
| 结束方式 | 正常 / 取消 / 超时 / 卡死被杀 / 进程意外退出 / 环境下线 / 服务重启 |
| 结束时位置 | 停在哪一阶段、哪一轮、哪一步 |
| 部分结果 | 中断前的有效尝试、命中（标「不完整，不给结论」） |
| 环境恢复结果 | 已恢复 / 已隔离（原因） |
| 结论与状态码 | §5.2 |

### 4.2 状态机

```
queued ─▶ waiting-env ─▶ preflight ─▶ running ─▶ finishing ─▶ done
   │           │              │           │           │
   │           │              └─不合格──▶ env-unfit   │
   └──取消──▶ cancelled（未开始，无需恢复）           │
                              异常（任一运行态）──▶ recovering ─▶ failed / interrupted / cancelled / timed-out
```

- 终态：`done`、`env-unfit`、`failed`、`interrupted`、`cancelled`、`timed-out`。非终态必须有活的进程和新鲜心跳，否则由看门狗或交叉检测修正（§3.4）。
- `recovering` 由恢复程序执行，不依赖任务进程；恢复结果写回任务记录。

### 4.3 收尾与恢复分层

| 层 | 触发 | 动作 |
|---|---|---|
| L0 正常收尾 | 循环结束 | 收尾检查（epilogue）→ teardown → 基线检查 |
| L1 进程内异常 | 抛错 / 偏离超限 / SKILL 失效 | `try/finally` 执行 teardown；写结束方式与位置 |
| L2 优雅取消 | 取消请求文件 / SIGINT / SIGTERM | 当前步骤结束后停 → L1 |
| L3 外部恢复 | 进程被杀、崩溃、卡死、断连（L0–L2 都没跑完） | 平台调用 `autotest env recover <envId>`（独立进程）：读台账与环境声明 → 逐项恢复 → 基线检查 → `ready` / `quarantined` |
| L4 交叉检测 | 平台重启、设备重新接入 | §3.4 |

- 看门狗（平台内）：心跳超时 30 s、进度超时（步骤预算 + 60 s）、总时长上限 → 杀进程树 → L3。
- 任务结果与进度改为**结构化文件**：`state/tasks/<id>/{task.json, events.ndjson, ledger.ndjson, result.json}`；平台不再正则解析日志（日志只给人看）。

## 5. P0：审批、命令行、状态码

### 5.1 审批（F3）

| 类别 | 判定 | 需要 |
|---|---|---|
| 被测软件内操作（含在允许清单会话中发消息、构造数据、替代执行） | 计划只用 SKILL Node 操作被测 App / Web | **默认允许**，自动批准（审计记操作者 `policy`） |
| 环境配置项（如 Taplus） | 环境声明 | 注册环境时按钮同意一次（§3.1） |
| **敏感计划** | 计划**额外**修改手机设置；操作被测软件之外的 App / 系统界面；单任务发送消息上限 > 50 条；系列次数 > 20 | Web 按钮同意 |
| 完全授权开启时 | — | 全部自动批准（审计记操作者 `full-access` 及开启人） |
| 硬约束（§9） | 删除 / 撤回消息、允许清单外会话、动锁屏 PIN、凭据落盘 | **任何情况下拒绝** |

- 完全授权：只能在 Web 上开关；开启后页面顶部常显红色横幅（谁、何时开启）；可随时关闭；开关写审计。
- 命令行没有「同意敏感计划」与「开关完全授权」的命令；遇到敏感计划返回状态码 30 + Web 链接。说明：本机无认证，这是**流程约束**而非安全边界，文档如实写明。
- 批准绑定：计划哈希、SKILL 版本、profile 哈希、App 版本、Issue 文件哈希、**允许的运行次数 / 系列次数**；执行时任一不符 → 31 / 32 / 33。
- 人仍可在审核页驳回任何计划（含默认允许的），并必须填写意见。

### 5.2 状态码（F8）

每个命令的 JSON 结果带三个字段：`status`（参考 HTTP 的三位数）、`code`（稳定字符串）、`exit`（进程退出码）。进程退出码为两位十进制，**十位 = 类别**；不用 1（Node 未捕获异常默认值，保留为「工具崩溃」），不用 ≥ 128（信号）。

| 退出码 | status | code | 含义 |
|---|---|---|---|
| 0 | 200 | `OK` | 命令成功，无结论（list / show / approve …） |
| 1 | 500 | `UNCAUGHT` | 未捕获异常（工具缺陷；保留） |
| 10 | 200 | `NOT_REPRODUCED` | 未复现 |
| 11 | 200 | `REPRODUCED` | 已复现 |
| 12 | 200 | `PARTIAL` | 部分实现 |
| 13 | 200 | `IMPLEMENTED` | 已实现 |
| 14 | 200 | `NOT_IMPLEMENTED` | 未实现 |
| 15 | 200 | `SUSPECTED_MISOP` | 疑似误操作 |
| 16 | 200 | `TURNED_BUG` | 转为 bug |
| 17 | 207 | `SERIES_DONE` | 系列完成（各次结论见 JSON） |
| 20 | 202 | `ACCEPTED` | 已受理（任务已排队） |
| 21 | 202 | `STILL_RUNNING` | `wait` 超时，任务仍在运行 |
| 30 | 403 | `APPROVAL_REQUIRED` | 需要人在 Web 同意 |
| 31 | 409 | `PLAN_HASH_MISMATCH` | 计划哈希不一致 |
| 32 | 409 | `PLAN_STALE` | 批准后版本变化（SKILL / profile / App / Issue） |
| 33 | 429 | `APPROVAL_EXHAUSTED` | 超出批准的运行次数 |
| 40 | 400 | `BAD_INPUT` | 参数错误 |
| 41 | 404 | `NOT_FOUND` | 对象不存在 |
| 42 | 422 | `PLAN_NOT_EXECUTABLE` | 计划不可执行 |
| 50 | 503 | `ENV_UNFIT` | 环境不合格（预检失败） |
| 51 | 423 | `ENV_LOCKED` | 手机锁屏，需人工解锁 |
| 52 | 503 | `ENV_OFFLINE` | 设备离线 / 浏览器不可用 |
| 53 | 423 | `ENV_QUARANTINED` | 环境已隔离，需人工处理 |
| 54 | 503 | `PLATFORM_DOWN` | 平台服务未启动（附启动命令） |
| 60 | 500 | `TOOL_FAILED` | 工具失败（执行失败且归类为工具） |
| 61 | 500 | `SKILL_STALE` | SKILL 失效 |
| 62 | 500 | `TASK_STUCK` | 任务卡死，被看门狗终止 |
| 63 | 500 | `TASK_CRASHED` | 任务进程意外退出 |
| 70 | 499 | `CANCELLED` | 已取消 |
| 71 | 504 | `TIMED_OUT` | 超出时长上限 |
| 72 | 410 | `INTERRUPTED` | 环境下线 / 服务重启导致中断 |

- 「执行失败」按失败归类落到 5x（环境）或 6x（工具）。
- 旧入口（`run / series / …`）保留旧退出码不变，并在 `--json` 中附新的 `status / code`；新命令一律用上表。
- 错误对象统一为 `{ status, code, message, hint, retryable, kind: env | tool | input | policy }`。

### 5.3 命令

`autotest <对象> <动作>`，旧入口保留为别名：

| 命令 | 作用 |
|---|---|
| `issue list` / `issue show <id>` | Issue 及分类、草稿 / 计划状态 |
| `draft create <id>` / `draft show <id>` | 生成草稿 / 查看（含 `PlanView`） |
| `plan explain <planId>` | 执行前说明：步骤、影响、不确定点、预计耗时、审批类别 |
| `plan approve <planId> --hash <h>` / `plan reject <planId> --note "…"` | 批准（仅默认允许类）/ 驳回 |
| `env list` / `env show <envId>` / `env check <envId>` / `env recover <envId>` | 环境状态、基线检查、恢复 |
| `task run <planId> [--env <envId>] [--series N] [--dry-run] [--idempotency-key K]` | 提交，立即返回任务 id（状态码 20） |
| `task status <id>` / `task wait <id> [--timeout S]` / `task cancel <id>` / `task list` | 异步任务管理 |
| `result show <taskId>` | `ResultView` |
| `help [--json]` | 全部命令、参数 schema、状态码表（Agent 可直接当工具定义） |

- `--json`：stdout 只有一个 JSON 对象；JSON 模式下所有日志（含 Midscene / Playwright / `console.log`）改走 stderr。
- 非 TTY 或 `--non-interactive` 时永远不提问。
- 命令行是平台服务的客户端；服务未启动 → 54。

## 6. P0：视图模型与 Web

### 6.1 视图模型

- `PlanView`：一句话目的；白话步骤（做什么、作用在哪个元素 / 目标、预期效果；模型选的目标标「运行时由模型选」）；判定规则白话；影响清单（发送消息数**上界**与会话、构造的数据、环境配置项、额外设置改动）；不确定点；模型调用点；预计耗时**区间**；审批类别。
- `EnvView`：状态、基线各项结果、租约、脏标记与原因、环境配置项、建议动作。
- `TaskView`：状态、阶段时间线、当前阶段 / 轮次 / 步骤、每轮结果、结束方式与位置、副作用台账摘要、环境恢复结果。
- `ResultView`：结论句、三行依据、有效尝试与区间、三个独立标识（证据复核、是否替代执行、工具自检状态[P1]）、失败归类与建议动作、证据链接。
- 白话步骤由 `node-specs.ts` 新增的中文模板字段（带参数插值）生成；报告首段 `leadOf` 复用同一套渲染。
- 预计耗时：有历史的计划用同计划最近运行清单的阶段耗时（中位数 ~ 最大值）；无历史用步骤数 × 步骤预算估算并标「首次估算」。
- 对象编号：计划 `<Issue>/<子用例>:<端>@<版本>`；草稿版本号递增；`schemaVersion` 为整数，只在破坏性改动时 +1。

### 6.2 Web 页面（P0）

每个页面回答：**要做什么 / 正在做什么 / 结果是什么 / 可信吗 / 下一步做什么。**

| 页面 | 内容 |
|---|---|
| 首页 | Issue 与任务列表及状态；**环境状态条**（每个环境的状态；锁屏红色提示「需人工解锁」；隔离显示原因）；完全授权横幅 |
| 环境页 | 基线逐项结果、租约、脏标记、环境配置项（首次同意按钮）、「重新检查」「恢复」「下线」按钮 |
| 计划审核页 | 一句话目的；白话步骤，每步在标定截图（`skills/teamily/refs`）上标出元素位置；判定规则白话；影响清单；不确定点；预计耗时；审批类别与理由；同意 / 驳回（驳回必填意见）；完全授权开关 |
| 结果页 | 结论句；三行依据；三个标识；证据；失败时归类与建议动作；中断时显示停在哪、环境是否已恢复 |

- 不引入前端框架（沿用 node:http + 静态 HTML/JS）；现有 `console.html` 旧任务类型保留，Issue 流程迁到新页面。
- 术语悬停解释：有效尝试、偏离、Wilson 区间、3/n 上界、替代执行、环境不合格、隔离。

## 10. 验收标准（P0）

1. **Agent 闭环**：一个**脚本化 Agent** 只读 `autotest help --json`、stdout JSON 与退出码（stderr 丢弃），完成 2010：生成草稿 → 计划默认允许自动批准 → `task run` → `task wait` → `result show` 拿到结论；另用 1 个敏感计划验证：返回 30 → 人在 Web 同意 → 再执行成功。另做一次 Claude 子代理演练（只给 `help --json`），只作参考，不计入通过判定。
2. **人能看懂（同事验收）**：一位未参与开发的同事只看计划审核页，**5 分钟内、不提问**，答对 6 问：发几条消息（上界）、发到哪个会话、会改哪些手机设置、怎样算复现、哪些地方不确定、大约多久。2010 与 1903 各一次。验收可在里程碑完成后安排，结果补记到 `docs/w2m3-acceptance.md`；未验收前该项标「待同事验收」。
3. **故障恢复**：注入矩阵——在 预检 / 准备 / 预热 / 循环中途 / 收尾 五个阶段，分别做 ①强杀任务进程 ②模拟卡死（注入步骤内长时间等待）③强杀平台服务后重启 ④`adb -s <手机> reconnect` 模拟断连（2026-10-29 由 `adb kill-server` 改来：后者会重启 adb 服务，测试机每次都因此掉 USB 调试授权、需人工点「允许」；`reconnect` 只踢开这台手机的连接）；每格至少 1 次（共 ≥ 20 次）。通过条件（全部满足，100%）：
   - 任务终态与注入一致，带正确的状态码、结束方式和停止位置；
   - 环境回到基线（§3.3 全部项通过），或进入 `quarantined` 且原因正确——**不允许出现「显示 ready 但基线不通过」**；
   - 不存在「进程已死仍显示运行中」的任务记录；
   - 紧接着的下一次正常任务得出结论。
4. **确定性**：执行哈希不一致 → 31；批准后改 SKILL 版本 → 32；超出批准次数 → 33（单测 + 各一次实测）。
5. **一致性**：同一结果在命令行文本、`--json`、Web 页面（Playwright 读取渲染后的页面）上的结论句、有效尝试、命中数、区间完全一致（自动比对）。
6. **不回退**：W2-2 的 `run / series / rerender / code-gate` 与控制台旧任务类型照常可用；2010、1903 各 1 次运行的**报告格式与字段**不变（结论值受服务端影响，不作要求）。
7. **代码门** ≤ 5 分钟，含新增的 schema / 快照 / 状态机 / 恢复 / 交叉检测测试。
8. **预计耗时**：真机门里每次运行的实际耗时落在 `PlanView` 给出的区间内的比例 ≥ 80%（不达标只记录，不阻塞，用于校准）。

## 11. 风险

| 风险 | 缓解 |
|---|---|
| 白话步骤与实际执行不一致 | 白话由 Node 模板与计划结构生成，不手写；快照测试覆盖每个模式 |
| 命令行重构破坏现有脚本 / 控制台 | 旧入口保留为别名并保留旧退出码；回归测试 |
| 恢复本身卡住或反复失败 | 恢复有总时长上限；失败即 `quarantined`，不重试成死循环 |
| pid 复用导致误判进程仍在 | 租约记录 pid + 进程启动时间，两者都吻合才算在 |
| 恢复要逐个打开触碰过的会话清输入框，耗时 | 台账只记真正键入过的会话；恢复时间计入门的耗时统计 |
| 手机锁屏使真机门长时间停住 | 锁屏即 `unfit`（51）+ 红色提示；真机门开始前人工确认已解锁且有人值守；故障注入不含锁屏 |
| 完全授权被遗忘长期开启 | 常显横幅；审计记录；（可选）超时自动关闭，待用户需要时再加 |
| Windows 收不到关窗口 / 断电信号 | 下次上线的交叉检测兜底（§3.4） |

  - `#onlineEnv` / `#startupCrossCheck` / `#orphanSweep` 处理接管、卡死、进程消失、无租约的「运行中」任务；`#offlineEnv` 先写取消请求，等待 ≤ 60 秒后强杀，再恢复或置脏，任务记 72。
- **调度** `platform/lifecycle/supervisor.ts#Supervisor`
  - 每 2 秒调度一次，每台手机同时只跑一个任务；每 5 秒跑看门狗。
  - 恢复在独立进程 `autotest env recover` 中进行；不合格的环境每 30 秒自动重检。

- **基线与恢复（§3.3）**
  - `platform/lifecycle/recover.ts#recoverEnv` / `#checkEnv`：先修复再检查，可重复执行，总时长上限 180 秒；修不好即隔离，遇锁屏 / 离线则记不合格。
