## 1. 参考：Artemis 的探索闭环（读 `ref/artemis` 核实）

| 机制 | 做法 |
|---|---|
| 两档执行 | **Flash**：单模型「观察 → 思考 → 执行」反应式循环，每步约 3–5 s，无规划者、无执行前校验、无检查者；可把多次点击串成一个序列抓住转瞬即逝的控件。**Pro**：多智能体图编排，每步约 15–40 s：规划者维护带里程碑和 `verify` / `assert` 检查项的 Markdown 计划；操作者照计划执行；单个动作先过执行前校验（树优先、像素兜底），多动作连发不校验；失败记「执行事件」留在操作者上下文里，直到后续动作成功；检查者只读，按 `off / final / checkpoints / strict` 四档核对检查点并做结束复核；可选输出者汇总报告 |
| 感知深度 | 元素定位三档：一次视觉检测 / 3 轮（树搜索 + 坐标核对 + 视觉）/ 8 轮（放大、OCR、目标检测、像素处理） |
| 历史 | 统一会话账本（相对时间 T+mm:ss）；较早截图换成视觉摘要，已完成步骤压缩成可检索的分块；不按步数截断 |
| 运行中干预 | 可向运行中的任务注入指令；持续监控类任务要显式释放才结束 |
| 测试准则（给 IDE 中的 Agent） | 先在真机上探索、确认真实的界面与跳转，再写测试，不凭空假设；探索有模型延迟，最终用例要写确定的等待；按任务性质选 Flash / Pro；「动态定位优先、坐标兜底」；先诊断再猜；多设备先问用户；凭据不经对话 |

## 2. 与 Issue 主线的分工（定位）

| | Issue 主线（现有） | 探索模块（本期） |
|---|---|---|
| 输入 | 一份 Issue | 一句话需求，或「在某区域里找问题」 |
| 目标 | 复现 / 验收一个已知现象，给出带分母的结论 | 发现未知问题、确认某功能能走通、为新页面积累 SKILL |
| 执行 | 预先标定的坐标，循环 ≤ 1 s、0 视觉 | 每步现场感知、执行前校验，秒级 |
| 判定 | 契约描述的现象 | 通用判定库 + 需求里写明的检查点 |
| 产出 | 结论 + 现场包 + 报告 | 发现清单（每条带证据与可重放的坐标操作）+ 覆盖情况 + 可转成 Issue 草稿 |

探索发现问题后，由它生成 Issue 草稿，**复现与统计仍交给主线**，探索模块不对「复现率」下结论。

## 4. 原则（继承 W2-3 / W2-4，本期新增）

- 继承：黑盒；结论只陈述事实；环境不合格不开跑；先记账再执行；生产构造只在允许清单会话；凭据不落盘；Issue 主线循环不变。
- **X1 先看再点，点前再看一眼**：每一步先取屏幕快照；单个动作执行前过执行前校验（W2-4 §4.3）；校验不过不点，记「执行事件」，下一步面对新屏幕重新决策。
- **X2 安全先于覆盖**：动作先分风险（H4）再执行；拦截记录可审计；只读探索默认允许，可写探索按敏感计划审批。
- **X3 发现要有证据**：每条发现都有现场包（录屏 / trace、日志、坐标操作序列）并经证据复核；复核不符的不计为发现。
- **X4 不替主线下结论**：探索只报告「看到了什么、在哪、怎么走到的」，复现率与「未复现」结论交给主线。
- **X5 「没发现」要带覆盖**：报告写清访问了哪些页面、试了多少元素、拦截了多少动作、因何停止，不写「没有问题」。
- **X6 可干预、可中断**：运行中可追加指令、取消；取消在步边界生效，照常收尾与恢复环境。

## 5. P0：快速档探索执行器（android-app、desktop-web）

### 5.1 单步闭环
1. **观察**：W2-4 屏幕快照（截图 + 规范化节点 + 来源 + 耗时）。
2. **决策**：多模态模型读「目标 / 需求、当前截图、节点列表（带编号）、压缩后的历史、已访问页面摘要、被拦截记录」，输出一个或一串动作：点击节点编号或坐标（附目标描述）、长按、键入（文字 + 目标输入框）、滑动 / 滚动、返回、等待、结束（附理由）。
3. **风险分类**（H4）：高风险 → 拦截并记事件，不执行。
4. **执行前校验**：单个动作走树校验 → 像素兜底；一串动作（用于转瞬即逝的菜单、提示条）只校验第一个，其余连发，任何一个失败即停。
5. **执行**：沿用现有黑盒驱动（坐标操作），先记副作用台账再执行（W2-3 G6）。
6. **异常门**：沿用驱动事件流（闪退、ANR、进程死亡、页面崩溃）；命中即写现场包。
7. **记录**：坐标操作日志（可重放）、轨迹事件（决策、校验结果、拦截、发现）、每步截图缩略。

### 5.2 历史与覆盖
- 会话账本：每步记「时间（相对开始）、页面指纹、动作、校验结果、结果画面摘要」；超过阈值的旧截图换成一句文字摘要，较早的步骤按段压缩，模型需要时可按页面或步号检索原始记录。
- 页面指纹：Android 用 Activity + 节点文字集合的哈希，Web 用路由 + 主要标题；记录访问次数与已试元素，供决策时优先未访问的入口、避免在一页打转（每页预算可配）。

### 5.3 上限与停止
- 步数、时长、模型调用次数、每页预算；连续拦截或连续执行事件超过阈值 → 停止并说明；目标达成（模型判定 + 检查点通过）→ 停止。
- 动作节奏不设 1 s 约束（每步含模型决策），但记录每步各环节耗时（观察 / 决策 / 校验 / 执行）。

## 6. P1：计划档（自然语言 → 带校验点的计划）

- **规划者**：把一句话需求拆成里程碑清单，每个里程碑可带 `verify`（应看到什么）或 `assert`（必须成立，否则视为发现）；计划以 Markdown 保存在运行目录，执行中允许修订，修订留痕。
- **操作者**：即 §5 的单步闭环，按当前里程碑行动。
- **检查者**（只读，同一套观察工具）：两级——「结束复核」（对照原需求判断是否达成、有无异常）与「检查点」（每个里程碑结束核对其 verify / assert）；判定按确定性优先：页面文字 / 节点存在 / 区域比对 → 视觉兜底（多数投票）。
- **执行前说明**：计划档启动前生成 PlanView 同构的「探索说明」（目标、里程碑、风险等级、预计步数与时长、模型调用上限、可能触及的会话），走 W2-3 审批。

## 7. P2：通用判定库（没有 Issue 时怎么判断「有问题」）

| 判定 | 方式 | 层 |
|---|---|---|
| 闪退 / ANR / 进程死亡 / 页面崩溃 | 驱动事件流（修正被测包归属，见 §0） | ① |
| 页面脚本错误 / 控制台错误 | Web 页面事件；只记可疑，复核后才算 | ① → 复核 |
| 白屏 / 空白页 | 截图像素方差 + 节点数量过少，持续 N 秒 | ① |
| 一直在加载 | 加载指示（转圈节点 / 区域）持续超过阈值 | ① |
| 错误提示 | 节点 / 页面文字匹配错误文案规则（失败、出错、重试、网络异常、Something went wrong 等，中英文） | ① |
| 占位文字 / 未渲染 | 方括号占位（如「[自定义消息]」）、未替换的模板变量、Markdown 源码泄漏 | ① |
| 点了没反应 | 执行前校验通过、执行后画面与节点均无变化，且该元素有可交互属性 | ① |
| 布局问题（截断、重叠、溢出） | 节点边界计算（超出屏幕、互相重叠的可点击节点）→ 视觉复核 | ① → ③ |
| 需求里写明的检查点 | 计划档的 verify / assert | ① → ③ |

- 每条判定命中 → 写现场包 → 证据复核（对照该判定的「现象描述」而非 Issue）→ 复核符合才进入发现清单；同一现象在同一页面去重。

## 8. P3：发现 → Issue 草稿 → 确定性复现

- 每条发现导出：现象、页面、触发路径（坐标操作序列 + 白话步骤）、证据（现场包、复核结论）、环境（运行清单）。
- 一键生成 Issue Markdown（摘要 / 复现步骤 / 预期 / 实际 / 频率 = 探索中命中次数 / 环境），写入 `issues/explore-<时间>-<序号>.md`，随后走现有「分类 → 契约 → 计划」流程；能编译成模式计划就编译，不能就由模型组合并标注；由人确认后用系列运行测复现率。
- SKILL 候选（H7）：探索中多次访问、文字指纹稳定的元素列入候选清单（页面、含义、指纹、坐标框、截图），人工审核后进标定流程。

## 9. P4：接入平台、MCP 与准则

- **任务类型**：W2-3 生命周期新增 `explore` 任务——租用环境、预检、副作用台账、取消、看门狗、恢复照常；审批：只读探索默认允许，可写探索为敏感计划（Web 同意）。
- **命令行**：`autotest explore run "<需求>" [--mode quick|planned] [--env <envId>] [--max-steps N] [--max-minutes M] [--max-model-calls K] [--writable]`；`autotest explore inject <taskId> "<指令>"`；结果用 `result show`（新增 ExploreResultView：发现清单、覆盖、拦截、预算使用）。
- **MCP**（W2-4 服务新增工具）：`explore_run`、`explore_inject`；结果资源为发现清单与各现场包。
- **Web**：任务页显示每步截图缩略、决策理由、校验结果与拦截；结果页显示发现与「转成 Issue」按钮。
- **测试准则**：
  - 给 IDE 中的 Agent：在 W2-4 `docs/agent-rules.md` 上补充「何时用探索、何时用 Issue 主线」「探索结论不是复现结论」「探索有模型延迟：需求里的等待时长按每步延迟折算」「多设备先问用户」「可写探索须由用户在 Web 同意」。
  - 给探索执行器自身的系统提示：先看清再点、不凭空假设跳转、点前确认目标、不确定就停下说明、不碰高风险动作、发现要描述可见现象而非猜原因。

## 11. 验收标准

1. **安全**：生产 android-app 只读探索 3 次各 20 分钟：副作用台账中无发送、删除、改设置、退出等动作；被拦截的动作逐条可查（类别与理由）；结束后环境回到基线。
2. **执行前校验有效**：报告列出每次运行的校验通过 / 修正 / 拦截次数；人为制造的界面漂移（例如在决策与执行之间滚动列表）被拦截或修正，不点错。
3. **能发现问题**：在可控的注入场景中检出：`am crash` 注入的闪退；W2-1 起已知会显示 Markdown 源码的引用块（2044 现象）或会话列表占位文字（若当时仍存在）；每条发现都经证据复核并带可重放的坐标操作。
4. **发现可转复现**：至少一条发现生成 Issue 草稿 → 计划 → 用主线系列运行给出带分母的结论（复现与否都可，口径正确即合格）。
5. **自然语言任务可用**：3 条一句话需求（如「看看个人主页的通知铃铛能不能打开」「在 Personal AI 里输入一段文字但不要发送，看看改写按钮的效果」「浏览 Artifacts 里的第一个文档」）在计划档下完成，检查点结论与人工观察一致。
6. **可干预**：运行中注入一条指令被采纳；取消在 1 步内生效并完成收尾与恢复。
7. **报告诚实**：未发现问题的运行写明覆盖、预算使用与停止原因；模型调用次数可见。
8. **不回退**：代码门全绿；Issue 主线 2010 / 1903 各 1 次结论口径不变；旧 mission / explore 入口照常可用（H5）。
