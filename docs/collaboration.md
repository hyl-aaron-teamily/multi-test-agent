# 协作方式

multi-test-agent 是 Teamily 客户端的黑盒测试台，从 2026-10-19 开始，全程只有两人开发：用户和 Claude Code。目标是不读源码，只做用户能做的事、只看用户能看到的现象，在 Android App、手机浏览器、手机视口网页和桌面 Edge 四个执行端上发现并复现问题，给出带证据、可复核、可重放的结论。项目最初是通用的「AI 视觉驱动测试平台」。M5 起转为 Teamily 专属、由 Issue 驱动；2026-10-31 收缩到两项能力，到 W2-5 定名为：快速档，按结构化文档（Issue、计划）反复执行、拦截问题；探索档，用速度和 token 换取发现新问题。用户负责方向和取舍：定范围、逐条审核规则（一次审过 121 条）、回答每期需求文档里的待确认项、批准合并、提供真机与测试账号、安装系统级环境、解锁手机、组织同事验收，并在发现偏差时及时纠正。Claude 负责其余工作：读代码与现场核实事实，起草里程碑文档与带推荐默认值的问题，实现、测试、真机验证，写验收记录与 CHANGELOG；获得授权后自主推进到合并。每期的节奏固定：需求文档 → 用户定稿 → 按子任务开发 → 合并前逐条报告完成标准（DoD）→ 用户同意后合并。

主要难点有四个。一是黑盒约束下结论要可信：准备阶段用模型定位、选目标，循环内只按冻结的坐标操作，间隔不超过 1 秒、不调视觉；检查类命中先经录屏证据复核再计数，结论给出有效尝试数和 Wilson 区间（例如开发期 1329 的一次「已复现」就由证据复核判为误报）。二是真机环境多变：Teamily 静默升级、深浅色主题切换、手机浏览器的无障碍树不跟随页面内跳转、页面响应慢几秒。对策是按 App 版本和分辨率缓存现场定位的结果，参考图过期就在循环外重新截取，手机浏览器上的页面状态改由视觉确认。三是安全：用的是生产环境，会接触真实用户。默认只读，硬约束（不删除 / 撤回消息、不出允许清单、不碰锁屏 PIN、凭据不落盘）在任何模式下都生效，点赞、关注等社交动作只在 agent 账号自己的内容上做；这条是用户看到 agent 点了真实用户之后定下的。四是规模失控：里程碑叠加让 TS 源码一度到约 2.4 万行，由用户审规则、按两项能力重构收敛。协作上也出过偏差，例如 Claude 曾把同事验收当成未完成的开发任务。用户的纠正都写进了规则文件和长期记忆，之后照做。

当前结果：W2-4.1 已合并到 `main`。两项能力在四个执行端可用；命令行、MCP（19 个工具）和 Web 控制台共用同一份视图模型；`docs/rules.md` 列出 111 条生效规则及其代码位置。样例 Issue 的结论如：2044 已复现；2010 在 10 次运行里有 4 次复现；1903 在 60 次有效尝试中未复现；两账号两端同步 8/8 送达；探索发现可以转成 Issue，再由快速档复现。新 Web 控制台的同事验收待进行。W2-5 已定稿，正在做第一阶段 P1 评测模式：用 Google 的 AndroidWorld 基准评测探索档。模拟器和 Python 环境已于 2026-11-03 装好。
